faq = [
  { q = "What is ISO 15118?", a = "ISO 15118 is the digital communication protocol between an electric vehicle and a charging station over the CCS cable — the one that carries authentication, the charging schedule and the control loop, as opposed to the analogue control pilot that only signals current limits. Part 2 (2014) is the first-generation application layer, part 20 (2022) is the second, and part 3 covers bringing the powerline link up. It is what makes Plug & Charge and bidirectional power transfer possible." },
  { q = "What does sans-I/O actually mean here?", a = "That no type in the crate opens a socket, reads a clock, or spawns a task. You call `handle_input(now, &bytes)`, then `poll_event()` to see what happened, then `take_transmit()` for bytes to write, then `poll_timeout()` to know when to call back. The transport, the clock, the randomness and the cryptography are yours.\n\nThe payoff is that the same protocol logic runs under Tokio on a charge-point back end and on a bare-metal vehicle controller, and that a complete DC charging session runs as a unit test in microseconds with time as a variable." },
  { q = "Which parts of ISO 15118 are implemented?", a = "ISO 15118-2:2014 (all 34 body messages), ISO 15118-20:2022 (`CommonMessages`, AC, DC, WPT and ACDP), and ISO 15118-3 (SLAC frames and the matching state machine for both roles). SECC discovery and V2GTP framing are covered too, along with the Plug & Charge signature profile.\n\nDIN SPEC 70121 is recognised in the handshake so a charger can decline it explicitly, but its message set is not implemented — the schemas are behind a paywall." },
  { q = "Does it do TLS?", a = "No, and it will not. A sans-I/O engine consumes bytes; where they came from is not its business. Bringing your own means `rustls` on a server and `embedded-tls` on a controller without this crate choosing for either.\n\nWhat is enforced is the part that is protocol rather than transport: `Protocol::Iso20::requires_tls()` is `true`, and SECC discovery refuses a security downgrade rather than silently accepting one." },
  { q = "Can I run it on a microcontroller?", a = "Yes. The protocol core builds for `thumbv7em-none-eabihf` with `std` off, and CI checks that on every change. You need an allocator — `alloc` is a requirement rather than a feature, because in bit-packed EXI a decoded string is a run of bit-shifted code points and can never borrow from the input.\n\nSet `max_payload_len` to what you can actually hold rather than leaving the one-mebibyte server default, and enable only the message sets you speak." },
  { q = "How is the EXI codec verified?", a = "Against a third implementation, not against itself. Every derived grammar — 298 of them — is diffed against `exificient`, the EXI reference implementation. Every one of the 121 message types is generated as a schema-valid instance, encoded by that reference implementation as a document *and* as a signature fragment, then decoded and re-encoded byte for byte by the generated codec.\n\nRound-tripping an encoder through its own decoder proves only that the two agree with each other." },
  { q = "Why does strict mode matter so much?", a = "ISO 15118 transmits no EXI options document, so every coding option is out-of-band knowledge. The one implementations get wrong is that fidelity is the *default* — `strict` is false.\n\nNon-strict grammars carry extra productions for content the schema does not declare. Those productions cost no bits of their own, but their existence widens every first-level event code: a grammar state with one declared production needs one bit non-strict and zero strict. Every element in every message is shifted." },
  { q = "How does it compare to OpenV2G, Josev and EVerest?", a = "OpenV2G is C, unmaintained, and ISO 15118-2 only. Josev is reference-quality Python — excellent for understanding the semantics, but unusable on a vehicle controller, and a garbage-collection pause inside a DC charge loop is a fault. EVerest's libiso15118 is modern and was actively developed, but it is C++, coupled to the EVerest runtime, and its EXI codec is generated C.\n\nWhat this crate adds is not the same thing in Rust: one codebase that runs on both a microcontroller and a back end, a wire format checked against somebody else's implementation, and the message-ordering rules — including the ones about failing — as shared data rather than as prose re-derived on each side." },
  { q = "Is Plug & Charge complete?", a = "The signature profile is: building, verifying, the algorithm restrictions, and the EXI-fragment canonicalisation that makes a signature interoperable. What is missing is the V2G public-key infrastructure — X.509 chain validation and the certificate-installation flows.\n\nThat matters, and it is stated rather than implied: verifying with a key you took out of an unvalidated certificate proves only that whoever sent the certificate also made the signature." },
  { q = "Do I need the ISO schemas to build it?", a = "No. The generated message sets are committed, so building or using the crate never touches the schemas. You only need them to *regenerate* the codec, and `scripts/fetch-schemas.sh` downloads the XSDs — which ISO publishes freely — reproducibly.\n\nThe spec texts are paid documents, and nothing in the build depends on having them." },
  { q = "Is it production ready?", a = "It is pre-1.0 and unreleased, and the API may still change. If your deployment needs certificate path validation, that part is yours to write today." },
